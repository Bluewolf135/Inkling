# Inkling roadmap — implementation plan for Tracks A–D

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans
> or superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`)
> syntax for tracking.

**Goal:** Take Inkling from "a PDF drawing layer that happens to run in
Obsidian" to "the reason the PDF is in Obsidian at all" — a safe write path,
ink that feels like ink, annotations that become searchable linked notes, and
enough product surface for someone other than the author to install it.

**Spec:** `docs/superpowers/specs/2026-09-05-roadmap-design.md`
(Track A's own design: `docs/superpowers/specs/2026-09-04-write-safety-design.md`)

**Tech stack:** TypeScript, `pdf-lib` 1.17.1 (pinned), `pdfjs-dist` 5.4.530
(pinned), Obsidian plugin API, esbuild, Vitest, GitHub Actions.

## Global constraints

Every task's requirements implicitly include these.

- **`isDesktopOnly: false`.** No Node or Electron APIs anywhere in `src/`,
  including transitively. Vault I/O goes through `Vault` or `vault.adapter`,
  never raw `fs`. (Tests under `tests/` run in Node and may use Node freely.)
- **No network calls at all.** No CDN assets, no telemetry, no update pings.
- **No new runtime dependencies.** Vitest is a devDependency.
- **Do not bump `pdf-lib` or `pdfjs-dist`.** Both pins are documented at
  `src/pdfView.ts:10`.
- Build DOM with `createEl`/`createDiv`; never `innerHTML`; user-facing copy
  in sentence case. Untrusted text (ink blocks, PDF annotation contents,
  extracted quotes) is set with `textContent`.
- Minimum Obsidian version 1.4.4 — don't reach for newer API.
- **No backups.** The vault syncs through Self-hosted LiveSync to CouchDB.
- `strict` and `noUncheckedIndexedAccess` are on. Indexed access yields
  `T | undefined`; handle it rather than asserting.
- **Commit after every task.** `npm run build`, `npm run lint`, and
  `npm test` must all pass before any commit.

# Phase B — Feel

## Task B.1: Stroke geometry as a pure module

The single source of truth for what a stroke looks like, so the canvas and
the PDF cannot disagree. Nothing renders from it yet.

**Files:** create `src/annotate/stroke.ts`, `tests/annotate/stroke.test.ts`.

**Interfaces produced:**

```ts
export type PathSegment =
  | { kind: 'move'; to: Point }
  | { kind: 'line'; to: Point }
  | { kind: 'quad'; control: Point; to: Point };

export const MIN_PRESSURE_SCALE = 0.35;

export function hasPressure(points: Point[]): boolean;
export function smoothedPath(points: Point[]): PathSegment[];
export function outlinePath(points: Point[], baseWidth: number): Point[];
```

- [ ] **Step 1: Write the failing tests.** Cover:
  - `smoothedPath([])` is empty; one point yields a single `move`; two points
    yield `move` + `line` (no curve to fit).
  - Three or more points yield `move`, `line` to the first midpoint, `quad`
    per interior point with that point as `control`, and a final `line` to
    the last point. Assert the segment kinds in order and that the last
    `to` equals the last input point exactly — a smoothed stroke must still
    end where the pen lifted.
  - Repeated identical points do not produce `NaN` control points.
  - `hasPressure` is true only when at least one point has a finite numeric
    `p`.
  - `outlinePath` returns a closed ring (first point equals last) with at
    least `2 * points.length` entries; its width at a sample with `p = 1` is
    `baseWidth` and at `p = 0` is `baseWidth * MIN_PRESSURE_SCALE`, measured
    as the distance between the two offset points generated for that sample.
  - `outlinePath` on two identical points returns `[]` rather than dividing
    by a zero-length normal.

- [ ] **Step 2: Run them and watch them fail** (`npm test -- tests/annotate/stroke.test.ts`).

- [ ] **Step 3: Implement `src/annotate/stroke.ts`.** Notes for the
  implementer:
  - Midpoint smoothing: `move` to `points[0]`, `line` to the midpoint of
    `points[0]`/`points[1]`, then for each interior point `i` a `quad` with
    `control = points[i]` and `to = midpoint(points[i], points[i+1])`, then a
    final `line` to the last point. This needs no lookahead and no tension
    constant — deliberately, because two renderers have to agree on it.
  - Normals: for sample `i`, use the direction of the segment from `i-1` to
    `i+1` (clamped at the ends), rotated 90°. A zero-length direction reuses
    the previous normal; if there is none, skip the sample.
  - The outline walks forward down one side and back up the other, so the
    returned ring can be filled with a non-zero winding rule.

- [ ] **Step 4: `npm test && npm run build && npm run lint`.** Commit:
  `"Add stroke geometry both renderers can share"`.

## Task B.3: Capture pressure and every coalesced sample

**Files:** modify `src/annotate/types.ts`, `src/annotate/pointer.ts`,
`src/annotate/controller.ts`.

- [ ] **Step 1:** In `types.ts`, add `p?: number` to `Point`, with a comment
  saying it is optional precisely so every annotation already in a vault and
  every `/Ink` read back still parses.

- [ ] **Step 2:** In `pointer.ts`, extend `toPoint` to read pressure:

```ts
	const toPoint = (event: PointerEvent): Point => {
		const rect = el.getBoundingClientRect();
		const scaleX = rect.width === 0 ? 1 : el.width / rect.width;
		const scaleY = rect.height === 0 ? 1 : el.height / rect.height;
		const point: Point = { x: (event.clientX - rect.left) * scaleX, y: (event.clientY - rect.top) * scaleY };
		// Pen only. A mouse reports a constant 0.5 while a button is down,
		// which would render every desktop stroke as a uniform ribbon at
		// half weight — worse than having no pressure at all.
		if (event.pointerType === 'pen' && Number.isFinite(event.pressure) && event.pressure > 0) {
			point.p = Math.min(1, event.pressure);
		}
		return point;
	};
```

- [ ] **Step 3:** In `onPointerMove`, at the point where it currently calls
  `getHandlers()?.onMove(toPoint(event), event)`, feed every coalesced
  sample instead:

```ts
		if (event.pointerId !== activePointerId) return;
		const handlers = getHandlers();
		if (!handlers) return;
		// A 120Hz stylus delivers several samples per frame and the browser
		// hands over only the last one unless asked. Everything else was
		// being discarded before smoothing ever saw it, which is most of why
		// fast strokes came out polygonal. Guarded because the method is
		// absent on some WebViews and returns an empty list on others.
		const samples = typeof event.getCoalescedEvents === 'function' ? event.getCoalescedEvents() : [];
		if (samples.length > 0) for (const sample of samples) handlers.onMove(toPoint(sample), sample);
		else handlers.onMove(toPoint(event), event);
```

  Leave the `onHover` call above it on the single event — a hover cursor does
  not need sub-frame resolution.

- [ ] **Step 4:** Check `handleMove`'s `draw` case in `controller.ts`. It
  pushes a point and redraws the overlay; with coalescing that is now several
  redraws per frame. Coalesce the redraw instead: push all points, redraw
  once. The simplest correct shape is to leave `handleMove` as it is and
  accept one redraw per sample — but measure. If it costs anything, add a
  `requestAnimationFrame`-gated redraw for the `draw` case only, and say so
  in the commit.

- [ ] **Step 5:** Verify `handleStart` records pressure too — it stores
  `point` directly, so it already does.

- [ ] **Step 6:** `npm run build && npm run lint && npm test`. Commit:
  `"Keep every stylus sample, and the pressure it came with"`.

- [ ] **Step 7: Device check.** On the S Pen: a fast stroke is smooth rather
  than faceted, and pressing harder visibly thickens the line. On a mouse:
  strokes are uniform, exactly as before.

		try {
			// A destination is either an explicit array or a name that has to
			// be looked up first. Wrapped because a malformed or dangling
			// destination is a property of the file, not a bug here.
			const explicit = typeof dest === 'string' ? await pdf.getDestination(dest) : dest;

## Phase E — Ink block performance (done)

Reported during Phase B: a note holding many ink blocks renders slowly.
Measured before changing anything, against the note that prompted it —
fourteen blocks, 1.8 MB, of which 1,797 KB is stroke JSON:

| | |
|---|---|
| Parse all fourteen blocks | 9.4 ms |
| Serialize one block (per save) | 1.3 ms |
| Canvas backing, two layers per block | 38 MB |
| The same, backed at display resolution | 118 MB |

The JSON was never the bottleneck. Every block mounted a base and an
overlay canvas whether or not anyone was looking at it, and backing those
canvases at display resolution — which is what made ink sharp — would have
tripled it.

Blocks now mount only within 400px of the viewport, the same trade the PDF
view makes for pages. Measured after, scrolling the same note end to end:
**peak 6 canvases and 7.4 MB with 9 blocks rendered**, about five times
less, with the canvas backed 1:1 against its displayed size instead of
stretched 1.5x.

Alongside it, four block problems found by reading the code:

1. Pressure was written but never read back, so a tapered stroke was
   redrawn flat by the block’s own save.
2. Undo history lived on the controller, which a block’s save destroys —
   so undo could not reach past the last pause. History became data rather
   than closures so any store can apply an entry, and now outlives the
   re-render.
3. Canvases were backed at the stored size and stretched to the column.
4. Coordinates were written at full float precision. Rounding to a tenth
   of a unit — under a tenth of a pixel as displayed — halves the stored
   size: 1,797 KB to 850 KB on that note.

### Still open

- **Existing notes do not shrink until each block is next saved.** A
  one-shot “Compact ink blocks” command would rewrite them all at once.
  Not built: it rewrites the user’s notes, so it is theirs to ask for.
- **A flat coordinate array** (`[x, y, x, y, ...]`) would roughly halve the
  stored size again, at the cost of a format version bump.

## Phase F — Ink block latency, stroke size, and block bounds (done)

Reported after Phase E: blocks still render slowly when scrolling, and notes
are too large. Phase E was right that the canvases were the memory problem
and wrong that the look-ahead was working.

**The look-ahead never ran.** Both of Phase E's observers were rooted at the
viewport, and an ancestor that scrolls clips a block to empty long before the
viewport does — so `rootMargin` bought nothing. Measured in the running app
against a block 73px below the fold with a 400px margin: `isIntersecting` was
**false** against the viewport and **true** against `.markdown-preview-view`.
Blocks therefore mounted at the instant they became visible and were drawn
late, which is exactly the symptom the margin existed to prevent. The root
has to be resolved after the block is in the layout, so it is now resolved a
frame later, the same reason `mountSurface` measures its width when it
mounts rather than at construction.

Alongside it, four changes:

1. **Mount and release are separate distances** — 400px in, 1200px out. One
   margin for both meant a block on the boundary re-mounted on every small
   scroll, and each cycle allocates canvases and redraws every stroke.
2. **The overlay's 2D context is acquired on demand.** Its element still
   mounts, because it receives the pointer events, but a block nobody draws
   on never allocates its backing store — half the canvas memory of a scroll.
3. **Built stroke paths are cached** in a `WeakMap` keyed on the annotation.
   Correct with no invalidation logic because the store replaces annotations
   wholesale rather than mutating them.
4. **Strokes are simplified when they commit** (Ramer–Douglas–Peucker,
   epsilon 0.5 surface units — under half a pixel as displayed). On commit,
   not on save: a save lands a second after the pen lifts, so simplifying
   there would visibly change the ink after the fact.

Measured, scrolling the same fourteen-block note end to end:

| | |
|---|---|
| Peak base canvases / memory | 5 canvases, 5.36 MB |
| Overlay backing store, scrolling only | none allocated |
| Points dropped by simplification | 73.2% |
| Serialized stroke JSON (40 synthetic strokes) | 342.9 KB → 94.5 KB (3.6x) |

**Drawing is now clamped to the block.** Pointer capture delivers every move
to the surface that captured it, wherever the pen actually is — so a stroke
dragged past the edge kept recording out there. Measured on an 800x450
block before the fix: x reaching 1200.7, y reaching -166.9, saved into the
note and invisible only because a canvas discards what falls off it. After:
0 to 800 and 0 to 450. Clamped rather than dropped, so the stroke slides
along the edge instead of being cut into pieces and rejoined across the gap.

## Phase G — A second way ink blocks lost work (done)

Found while asking whether the Phase-A/d9bdb47 fix covered everything: it
did not. That fix handled a save that could not *find* its block. This is a
save that finds it and writes somewhere that does not last.

`findOpenEditor` returned `view.editor` for any MarkdownView showing the
note, without checking its mode. An edit made through a **reading-mode**
view's editor is silently discarded — measured in the running app:
`replaceRange` changed the buffer, left `dirty` false, never reached disk,
and was gone the moment the view re-synced from the file.

That made it the worst shape of failure. The write did not throw, so the
save counted itself a success, cleared the `unsavedInk` recovery entry that
exists precisely to survive a failed save, and left the drawing on screen
with nothing in the file — until the next re-render took it. The recovery
mechanism was defeated by the save reporting success.

So drawing in an ink block in **Reading view** lost the work. Live Preview
and source mode were unaffected, which is why it went unnoticed: both report
`'source'`, and only reading view took the broken path.

Reading-mode views are now skipped, which sends the save to `vault.process`
— the path that works regardless of what is open. Verified end to end: a
stroke drawn in an ink block in reading view now lands on disk.

### Still open

- **`unsavedInk` is in memory only.** A save that genuinely fails still
  keeps the ink alive across a re-render, but not across quitting Obsidian.

### Bug: extraction invents annotations in a PDF that has none (fixed)

Fixed 2026-09-06, and it turned out to be four bugs rather than one. All of
them came from reading pdf.js fields that do not exist in pdfjs-dist
5.4.530, and the last of them forced a change of approach.

1. **No subtype filter.** Every annotation object was a candidate, so the
   book's 201 /Link annotations became highlights of their own chapter
   titles. Only markup annotations are read now — the specification's own
   distinction — which took that book from 207 entries to 7.
2. **/Contents arrives as `contentsObj: { str, dir }`**, not a `contents`
   string, so every comment extracted as empty.
3. **Note annotations vanished entirely**, a consequence of 2: with no
   comment text and no words underneath, the "neither quote nor note" guard
   dropped them.
4. **/NM is not exposed by pdf.js at all** — no field carries it. So every
   annotation read back as foreign however plainly it was ours, and block
   references were derived from a position rather than the stable `ink-` id
   sitting in the file, so they changed whenever an annotation moved.

The fourth could not be fixed by reading pdf.js more carefully, so the
reader changed: **pdf-lib now reads the annotation dictionaries and pdf.js
reads only the page text.** Each does the half it can. Nothing extra is
written into anyone's PDF — it already carried all of this, and the file
stays self-contained and readable by any other PDF app, which was the point
of putting annotations in it. Extraction remains strictly read-only.

Two things came back for free. The private `/Inkling /Q` quote, stored when
a highlight is drawn, is finally read — so **a scanned page with no text
layer now extracts**, which it never could before. And the text layer is
only touched for annotations without a stored quote, so pdf.js is often not
loaded at all: the 195-page test book extracts in 489ms.

Verified end to end in the running app. The book's fourteen ink annotations
had always been the user's own; nothing could tell, because /NM was
invisible. They now extract as seven entries with colour labels rather than
hex, no false "external" marks, and `^ink-` block references.

This module also had no tests, and could not have had any: it reached
PRESET_COLORS through the annotate barrel, which re-exports the toolbar,
which imports the Obsidian API, so importing the whole of PDF reading into
Node failed. It takes the constant from annotate/types directly now, vitest
resolves pdfjs to the legacy build Node needs, and there are twelve tests.

### Original report

Reported 2026-09-06: extracting from a test book with no highlights and no
annotations still fills the annotations note.

**Lead, from reading rather than from running it** — not yet confirmed
against the book in question. `collectAnnotations` (`src/extract/extract.ts`)
calls `page.getAnnotations()` and never filters on `subtype`. The
`RawAnnotation` interface declares the field and the module comment mentions
it, but the loop never reads it. So every annotation object in the file is a
candidate, including `/Link` (tables of contents, cross-references, external
URLs), `/Widget` (form fields) and `/Popup`.

`quoteUnder` then recomputes the text under the annotation's rectangle — and
a link's rectangle sits directly on top of the text it links from. So each
one produces a non-empty quote, survives the `if (!quote && !note) continue`
guard that was meant to drop contentless annotations, and is emitted. They
would all be marked `· external`, since a link carries no `ink-` name, and
come out at the default colour, since links usually carry no `/C`.

Fix to consider: allow only the subtypes that represent something a person
marked up — `Highlight`, `Underline`, `StrikeOut`, `Squiggly`, `Ink`,
`Text`, `FreeText`, `Square`, `Circle`, `Polygon`, `PolyLine` — and exclude
`Link`, `Widget` and `Popup` outright. Confirm against the reported book
first, and add a regression test with a PDF carrying a link annotation over
text, since that is the case no existing test covers.

sweep found a fourth nobody had reported, the toolbar groups that made
"collapse" not collapse. There is now one rule for all of them, keyed on
the class prefix, and it must stay last in `styles.css`.

The lesson generalises past CSS: three of the day's bugs were a correct
mechanism wired to something that quietly ignored it — an observer rooted
at the viewport, an editor write into a buffer nothing persists, an
attribute an author rule outranks. None of them threw.

### Queued

- ~~Block parsing is still eager.~~ Dropped 2026-09-06, on measurement.
  Compaction took the cost with it: the 39-block, 486 KB Newton's Laws note
  parses every block in **3.85 ms**, and reading only the ids costs 3.12 ms
  of that — `readInkBlockId` still runs a full `JSON.parse`, so deferring
  the validation saves under a millisecond. Avoiding the parse entirely

  is further from being one now. A flat coordinate array would shrink this
  again as a side effect.
- ~~Move and resize are not clamped.~~ Done 2026-09-06: a selection dragged
  or resized past the edge now stops at it. Measured before, an 800x450

- **`unsavedInk` is in memory only** — it survives a re-render, not a quit.
- **Incremental PDF save**, the largest remaining win: it would remove the
  whole-document re-serialize, and with it the size-scaled save throttle in
  `pdf/saveCadence.ts` and the up-to-a-minute of ink a crash can cost.
- **A flat coordinate array**, for another halving, at a format version bump.
- **A way out of a malformed block.** Raised 2026-09-06, after a
  Self-hosted LiveSync conflict on "Motion in 2-D Exercises" left the
  refusal banner on a block. That file turned out to be healthy — all five
  blocks parsed, 96 and 100 annotations intact, nothing duplicated — and
  the banner was stale, but the episode showed two real gaps.

  First, the decision is made once when a block renders and is never
  revisited, so a banner outlives the condition that caused it and only
  clears when something re-renders the note. It should re-check.

  Second, and the reason this is worth building: if a block really is
  malformed there is no way out from inside Obsidian. The user is left
  hand-editing JSON. Refusing to save over what we could not read is the
  right call and should stay, but it should be the start of a recovery
  rather than the end of the road — show what survived the parse, say what
  did not, and let the user keep it deliberately. Conflicts will keep
  happening in a live-replicating vault, so this will come up again.

- ~~Integration coverage.~~ Done 2026-09-06. `tests/harness/surface.ts`

  It caught two of its own faults immediately: assertions passing against an

## Deferred — block captions

An ink block is invisible to search: a page of handwritten physics is, to
Obsidian, a JSON blob. An optional caption rendered beneath the block would
make it findable, linkable and readable by a screen reader — the same
argument extraction makes for PDFs.

The user is undecided about whether it fits how they work, and asked that
it be a setting if built. So: build it toggled off, with the toggle in the
settings tab, and let it prove itself.
